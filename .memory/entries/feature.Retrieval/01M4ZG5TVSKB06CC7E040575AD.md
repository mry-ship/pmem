结论：检索时按当前代码核对记忆（stale 过期/失效），必须扣除“记忆自己那次修复”的提交，否则误报很多。

规则：满足任一条就标 stale，原因写进 check：锚点文件已不存在；找不到锚点符号；文件在核对基准日之后又改过。
- 基准日 = max(写入日, verified)。
- 如果记忆文件在写入后 7 天内提交（或还是本地未提交的草稿，按今天算），基准日取提交日。通常先写记忆、过一两天才连同代码一起提交，这次提交属于同一份工作。
- 隔了很久才提交的（如导入的旧记忆）仍以写入日为准。

证据：TileMatch 256 条带锚点的记忆用真实 SVN 提交日期核对，31%（79 条）会标 stale，其中 29 条的改动在写入后 3 天内，基本就是修复本身的提交。

其他要点：
- 改动日期向版本库批量查询（Git 一次 log 加一次 diff，SVN 一次 info 加一次 status），缓存 60 秒，只核对选中结果的锚点。
- 检索加核对共 30–200 毫秒。
- 没有版本库时退回看 mtime，误报多：TileMatch 837 个脚本里 102 个 mtime 是当天，被 Unity 或工具碰过，所以有版本库就必须用版本库日期。

同义词：TileMatch 里“闪退”0 条、“崩溃”28 条。在 modules.yaml 加 synonyms: [闪退, 崩溃, crash] 后，在 Jigsaw 的 87 条里搜“拼图 闪退”，前 2 条就是两条提到崩溃的记忆。扩展词按 0.8 权重计入。条目的 aliases 只并入本条的索引，不参与扩展。
