# 编码后审查

审查对象是本轮实际改过的文件。以 diff 或文件内容为准，不以复述为准。

## 触发条件

只在用户明确要求「最小审查」或「按 pmem-review」时执行，不因新增文件、跨模块或改了对外契约、持久化数据、权限、资源生命周期、失败语义而自动触发。

没有点名审查时，不强制完整审查。用户明确要求审查时，即使只改了一个文件，也要执行。

## 检查

1. 从相关模块的规格、排除项、决定和功能记录摘出必须保持的行为、接口和约束，只对这次 diff 涉及的模块逐条标状态。字段名和须按字面抄的原文用 `pmem spec closed`。行为是否仍成立由审查判断。带「待对照代码核对」的预填不能标成违反。不自动改规格，不把代码推断写成新的设计事实。
   - 未触及：本轮 diff 没有涉及该约束
   - 符合：有足够证据表明没有违反
   - 违反：有明确代码路径和证据表明破坏了约束
   - 待核实：当前证据不足以判断
2. 核对调用方、接口、数据结构和旧数据兼容。
3. 标出重复实现、用不上的抽象、不必要的依赖和配置。判断要有调用方或引用证据。
4. 核对异常、边界、安全、资源释放、生命周期和并发。
5. 跑项目里已有的验证。优先使用 harness.verify_commands、README 或仓库里现成的测试、编译和静态检查。不新造一套验证命令。Unity 用项目已有的编译或测试方式。
6. 验证失败就先定位原因，不宣称完成。跑不了就写明没跑什么、因此没覆盖什么。
7. 当前环境能另起一个只读 Agent 时，把 diff 和本清单交给它复核，不要先把结论告诉它。不能另起就写明未做独立复核。

## 不做

- 不把风格偏好写成缺陷。
- 不为了减少行数删除异常处理、测试、安全检查或用户点名的行为。
- 没有代码路径和证据的问题不报。

## Unity

触发条件与 pmem-minimal 相同。对照实际 diff 检查资源释放、对象池、JNI、广告回调、异步取消、线程边界和 ANR。相关代码没改到就不要展开。

## 输出

结论是「可以交付」或「先改再交付」。约束核对逐条一行，状态只写未触及、符合、违反、待核实。违反和待核实写路径与证据，未触及和符合不展开。另写不能删的逻辑、验证命令和结果、独立复核做了没有。有问题先改，再只复查失败项。
