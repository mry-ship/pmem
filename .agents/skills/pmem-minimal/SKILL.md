# 编码前决策

先决定这次该不该做、能不能复用，再写代码。简单修改不把本技能走完。

## 何时停在轻量流程

同时满足下面几条，就只做两步后停：说明现有改法已经够用；确认没有更小的现有实现。不比较方案，不拆任务。

- 只动一个已有文件
- 不改变对外行为
- 不新增文件、依赖、模块或抽象

其余改动走下面的完整流程。缺陷修复也走完整流程。

## 完整流程

1. 需求判断。用户是否明确要这个行为；它是否解决现有问题；有没有更小的做法；是否只为结构好看。不必要就说明理由并停，不开始实现。
2. 查记忆。对要改的文件调用 search_memory，传入要改的路径。模块不明先 list_modules。本对话已查过的模块不重复查。MCP 不可用时改跑 pmem search --module 与 --brief。返回失败不算查过，写明没查到，继续查代码。标为 stale 的先对照代码。采纳排除项、风险、更正和功能记录里必须保持的行为。
3. 查规格。只有 .memory/config.yaml 的 spec.read_before_edit 为 true，或用户明确要求读规格时才做这一步；否则跳过，不主动打开 .memory/specs。要做时：若有该模块的程序设计，按字面读入参出参闭集、失败条件和原文模板。若有模块现状，读必须保持的行为。带「待对照代码核对」的预填，以及仍有空标记的节，先对照代码，不当成已生效约束。没有规格，或检查虽通过但正文仍是增量摘要，就说明限制，继续以代码和记忆为准。不运行 pmem spec complete。
4. 查代码。找现有函数、调用方、已有依赖和技能。检索结果里若有 context 节，读常一起改的文件和近期修复。不要为此打开 harness。
5. 选方案。按这个顺序，停在第一个够用的：复用现有实现，扩展现有实现，使用已有依赖，使用标准库或平台能力，引入新依赖，新建模块或抽象。选后面的，要写明前面的为什么不行。
6. 缺陷先写根因。写清现象、证据路径、为什么不是别的原因。根因不清就继续查，不改代码。
7. 列出不能省略的部分：调用方、数据流、异常和边界、测试、安全与权限、资源释放、生命周期、并发和线程。
8. 只有复杂任务才拆解。复杂指多个模块、多段可独立交付的行为，或用户要求先出计划。验收条件写成可观察的结果。简单任务不列任务清单。

用户坚持更重的方案时照做，并把被放下的更小方案用 record_memory 写成 exclusion。

## 临时妥协

只有确实用了临时简化才记录。用现有 decision 或 risk，不新增字段。正文写当前方案、为何现在可接受、限制、何种条件必须升级、升级后的方向。applies 写限制，verify 写升级条件。不把临时做法写成永久结构。

## Unity

仅当 .memory/config.yaml 的 project.type 为 game，或仓库有 Assets、Addressables、JNI、广告 SDK 时才检查：资源加载与释放、对象池和 UI 生命周期、JNI 异常、广告初始化和回调、异步取消和竞态、主线程与后台线程、Unity 与 SDK 版本、内存、性能和 ANR。不能为了短而绕开这些约束。

## 输出

完整流程交付这几段：需求判断、已有能力、候选方案、推荐方案、不能省略的部分。复杂任务再加拆解和验收条件。有临时妥协再加妥协记录。
