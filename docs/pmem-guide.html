pmem：插拔式、托管式的 AI 项目记忆系统

插拔式：一条 pmem init 接入任何项目，不改业务代码；不想用了，删掉它生成的配置即可。
托管式：接入后绝大部分时候不需要你手动操作。查记忆、写记忆、忘查时拦截、改完没记时提醒，全部由 AI 和 Hook 自动完成，你照常提需求、修 bug 就行。
记忆是仓库里的 Markdown 文件，跟代码一起提交、团队共享，不需要服务器，也不上传任何数据。支持 Cursor、Claude Code、Codex。

一眼看懂

① 绑定一次pmem init 生成规则、Hook、MCP 配置，挂到 AI 工具上
→
② 改前自动查AI 要改某个文件，Hook 定位所属模块；没查过记忆就拦下，直到查过
→
③ 按模块记改了模块就写功能记录（需求来源、必须保持的行为）；有排除的方向、根因和坑、约束、方案取舍再写教训，都是 .md，附一句话标题
→
④ 结束自动追问改了模块却没写记忆，Hook 追问一次有没有新教训
→
⑤ 随代码共享记忆跟代码一起提交，队友拉代码就能查到

核心特点

  • 挂载式：不改代码，也不改工作方式
  • 自动触发：Hook 改前拦截、结束提醒；出错直接放行并提醒一次，不卡开发
  • 按模块寻址：改哪个文件就查哪个业务模块
  • 本地 + 团队共享：记忆在仓库里，Git / SVN 均可
  • 不用过期结论：关联代码变了标“需核实”，新结论替代旧结论
  • 省 token：每次只返回最相关的几条，与总量无关

三步接入（约 5 分钟）

# 1. 安装（每人一次）
uv tool install "pmem[embed] @ git+https://github.com/mry-ship/pmem"
# 2. 项目根目录绑定（每个项目一次）
pmem init --type game
# 3. Cursor 设置 → MCP 启用 pmem，
#    对 AI 说“按 pmem-bootstrap 技能划分模块”
pmem doctor

队友拉代码后只需安装并打开 MCP 开关。详见 在其他项目接入。

pmem 是什么

pmem 把研发过程中得出的结论（根因、排除过的方向、方案决定、风险）按业务模块存成 Markdown 文件，放在仓库的 .memory/ 目录里，跟代码一起提交、评审，整个团队共享。

  • 不需要服务器和数据库：记忆就是仓库里的文件；检索索引只是本机缓存，删了能重建。
  • 按模块寻址：改哪个文件，就自动查那个文件所属模块的记忆。
  • Agent 主动 + Hooks 兜底：规则告诉 AI 何时查、何时写；它漏了，Hooks（工具调用前后的拦截脚本）会提醒，任何异常都直接放行（随后提醒一次），不会卡住开发。
  • 问答也审查：读到哪个模块的代码，就附上该模块现行结论的摘要；问题提到的模块本轮没查过，回合结束时要求 AI 查过再核对回答。
  • 收益可量化：pmem report 统计命中率、避坑次数、跨人复用；pmem bench 做有记忆 / 无记忆对照实验。

核心概念

模块 module

格式 category.Module，如 gameplay.Jigsaw；子模块用点号续写，最多 4 段（见下文“父子模块”）。模块是业务单元而不是目录，可以包含多个路径、起别名。定义在 .memory/modules.yaml。

议题 entity

模块内的子话题，如 Reward、Config。检索时议题匹配会加分。

记忆条目

一条记忆一个文件：.memory/entries/<模块>/<ULID>.md。ULID 是按时间排序的唯一编号。写入后正文不再修改。

替代 supersedes

要推翻旧结论就新写一条，在 supersedes 里填旧 id。旧的自动从检索中隐藏，但文件仍保留在版本库，可按时间回溯。

关联代码 anchors 与过期 stale

anchors 记录相关代码（文件#方法）。代码在记忆写下后改过或被删，检索结果标 stale: true，提示用前先核对。

别名 aliases 与同义词 synonyms

写记忆时把现象的其他叫法填进 aliases；团队常用同义叫法登记在 modules.yaml 的 synonyms，检索时自动扩展。

状态 status

active 正式；seed 种子，从提交说明和文档提炼、待负责人确认，能检索到并标“种子，待确认”；draft 草稿（write.default_status: draft 时）；archived 已归档，不再出现在检索里，它替代过的旧记忆也保持隐藏。归档时记下日期和原状态：带 as_of 回看时，那天之后才归档的仍然可见；恢复时回到原状态（退回的种子恢复后仍是种子）。

父子模块

大业务需要细分时，子模块用点号续写名字，最多 4 段（大类 + 3 层），父子关系由名字表达，不需要另写 parent。以“4 个广告 SDK、每个 SDK 有自己的渠道、iOS 和 Android 打入的 SDK 不同”为例：

modules:
  system.Ads:                  # 父模块：广告公共逻辑（瀑布流、隐私弹窗时机）
    paths: [Framework/Ads/Core/**]
  system.Ads.AdMob:            # 子模块：AdMob 适配
    paths: [Framework/Ads/AdMob/**]
  system.Ads.AdMob.Mediation:  # 第 4 段：AdMob 下的聚合渠道
    paths: [Framework/Ads/AdMob/Mediation/**]
  infra.Build:
    paths: [Build/**]
    related:                   # 名字看不出的深层关联
      - { module: system.Ads, reason: 打包按平台选择打入的广告 SDK }
  • 查：查子模块会带上各级上级模块的教训（在本模块的 5 条之外另给最多 2 条，search.inherit_max 可调；本模块教训不够 5 条时空出的位置也给上级），结果标“上级 system.Ads”；功能记录不继承。查父模块时附上各下级模块的条数和最新 5 条记忆的标题（含更下级，教训和功能记录都算），不给全文：问“广告系统整体情况”时一次看到各 SDK 的要点，要细节再查对应子模块。
  • 写：结论写在适用的最高一层，对所有 SDK 都成立的写到 system.Ads。兄弟模块写了同议题的教训时，写入结果会提示改写到父模块；父模块的记忆可以 supersedes 下级的，反过来不行。
  • 闸门：子模块自己没有记忆、但上级有教训时同样拦截，拦截提示里附上上级的坑。
  • 登记：父模块必须先登记（可以只作分组、不写路径），文件归属按最具体的路径。父模块已登记时，写入未登记的子模块名也会接受。
  • 平台和渠道不是一层：iOS/Android、渠道、版本差异写进记忆的 applies；只有各自有独立代码目录时才拆成子模块。
  • 维护：pmem migrate rename 改父模块时子模块跟着改名；pmem sync 会提议把大模块里文件多或改动多的子目录拆成子模块（只提示）；pmem health 的“父子模块结构”一节列出缺父模块、只有一个下级的空父模块、兄弟模块重复的教训等。团队成员需升级到支持父子模块的 pmem，旧版仍能读写已登记的子模块，但没有上级教训继承。

五种记忆类型（kind）

kind含义典型场景
conclusion结论根因确认、改完验证通过后的结论
exclusion排除项某个方向试过不行，别再走（检索时略微加分）
correction更正旧结论已不成立，配合 supersedes（检索时略微加分）
risk风险改动这里要注意的坑
decision决定方案选型和取舍理由
feature功能功能记录：改了模块就写。需求来源、必须保持的行为、适用条件、入口；检索时只列标题
plan规划还没实现的需求，不当现状；实现后由功能记录替代

前五种是教训，检索时给全文、排在前面；后两种是功能记录，检索时单独一组、只给标题（默认最多 3 条，search.feature_limit 可调），要全文按 id 取。这样功能记录写得再多也不会挤掉教训。

一条记忆长什么样

---
id: 01M4X6AZN6N1AX9M6E6P34SRX4
module: gameplay.Jigsaw
entity: Reward
kind: exclusion
author: zhangsan
note_date: '2026-10-14'
anchors: [Assets/Game/Jigsaw/JigsawReward.cs#Claim]
summary: 断线重连重复发奖的根因在服务端，不要在客户端去重
verify: 断线重连后领取，服务端日志只有一次发奖
---
拼图奖励在断线重连时会重复发放：服务端 Claim 接口没有按关卡做幂等校验……不要在客户端做去重。

四个可选字段：

  • summary：一句话标题（60 字以内）。读代码摘要、拦截提示、Wiki 和同一对话里的重复检索只显示它；没填时取正文第一句并去掉“决定：”这类前缀。
  • verify：怎么确认问题已解决或结论仍成立（命令、测试名、现象），下次遇到同样的问题直接验证。
  • applies：这条在什么前提下成立（平台、配置、版本、场景，120 字以内）。检索结果会提醒 AI 先判断前提是否满足，不满足就不套用。
  • scope: project：全项目都会踩的坑（编码、环境、跨模块约定）。读任何模块的代码时，都会附上本对话还没给过的至多 3 条全项目级排除项、风险、更正，Wiki 首页单列“全项目通用”。

旧版 pmem 读写带这些字段的文件不会丢字段；但 feature、plan 两种类型需要新版本才认得，旧版会跳过这类文件，团队请一起升级。

在其他项目接入

前提：已安装 uv（Python 包管理工具）、Python ≥ 3.10，以及 Cursor、Claude Code、Codex 中至少一个。项目用 Git、SVN 或都不用均可。
  1. 安装 pmem每人一次

    本机已经装好（以可编辑模式从本仓库安装，改本仓库代码立即生效），可以跳过。其他同事按下面任一方式安装：

    # 方式 A：从 GitHub 安装（推荐团队使用）

uv tool install --reinstall "pmem[embed] @ git+https://github.com/mry-ship/pmem"

# 方式 B：拿到本仓库源码目录后，在该目录里执行
uv tool install --editable ".[embed]"

# 验证
pmem --version

    [embed] 启用中文语义检索，首次使用下载约 90 MB 模型，所有项目共用。去掉它则只用关键词检索。

  2. 在目标项目根目录初始化每个项目一次 
    cd D:\Work\MyGame

日常使用

正常写需求、修 bug 即可，基本不用手动操作。一次典型对话的流程（左侧色带是环节，①②③ 是 Agent 要主动做的三步）：

1. 改代码前查Agent 按要改的文件调用 search_memory(path=...)，同一模块一个对话查一次。
→
2. 用之前核对结果带 stale: true 的，打开关联代码核对；仍成立就 confirm_memory，不成立写 correction。
→
3. 按模块写每个改过的模块写一条功能记录（谁要求的、为什么、必须保持的行为）；另有试过不行的方向、根因和坑、看代码看不出的约束、方案取舍时，各写一条教训。只改测试、生成代码、配置的不用写。
→
4. 结束追问AI 在回复开头写“【pmem检索】模块（要点）”，结尾分行写“【pmem查询】模块，用到「…」”和“【pmem修改】模块 已写功能记录「…」；模块 无需记录（原因）”。只有改了模块却既没写记忆、也没在结尾说明无需记录时，回合结束才追加提醒。不需要你回复。Cursor 会把它显示成一条以“[pmem]”开头的用户消息，由 AI 处理。

写记忆的约定

  • 正文自包含：教训写现象、原因、证据、影响范围；功能记录写需求来源、必须保持的行为、适用条件、入口。都不写“改了哪个方法”这类版本库已有的信息。
  • 写一句 summary（教训写结论，功能记录写“什么行为必须保持”）；结论和更正尽量写 verify；有前提的写 applies；改哪里都会踩的坑加 scope: project。没填 summary、决定没写取舍、读起来像变更记录、功能记录没写需求来源时，写入会返回提示（不拒绝）。
  • 还没实现的需求写成 plan；实现后写功能记录并在 supersedes 填那条规划的 id。
  • 正文 20～5000 字，超过 600 字会提示精简。不写密码、密钥、个人信息，含疑似密钥会被拒绝。
  • 写入会返回 similar（同模块最相近的已有记忆）：重复或推翻了某条，就带 draft_id 重写并在 supersedes 填旧 id。
  • 同一任务对同一模块只留一条：再次写入时带上次返回的 draft_id 覆盖。覆盖时没填的 supersedes、anchors、aliases、summary、verify、applies、scope 沿用原值。
  • 同一议题每天最多写 5 条，防止刷屏。

闸门（Hooks）

闸门是兜底机制：Agent 忘了查记忆就去改“已有记忆的模块”时，Hooks 会拦下这次修改，告诉它该调用什么。

模式行为
block（默认）本对话没查过该模块就一直拒绝修改，检索真正返回结果后放行（调用失败、终端输出被丢弃都不算）；只放行查过的那个模块
warn首次修改时拒绝一次，之后放行
off不拦截，只靠规则
  • 拦截范围：写文件类工具（Write / StrReplace / Edit / Delete 等）和终端里的写命令：重定向、Set-Content、cp/mv/Copy-Item、git checkout/restore/apply、python -c 及所运行脚本里写文件时的字面路径，先 cd 再写相对路径也能认出。同一条命令里带 pmem search 只放行查过的模块。
  • 事后比对：脚本里拼出来的路径、格式化工具、git stash/reset 这类事前看不出写了什么的命令，执行前后各比对一次未提交文件（Git、SVN 都支持），改到没查过的模块时立即提醒 AI 补查。命令已经执行完，所以只能提醒、拦不住；仓库大到单次比对超过 1 秒时暂停 24 小时；git、svn 的只读子命令（status、log、diff 等）不做比对。
  • 别的记忆服务也叫 search_memory 时，它的结果不算“查过 pmem”。
  • 拦截提示里直接列出该模块现行的排除项、风险和更正（最多 5 条）、关联代码就是要改的这个文件的功能记录，以及本对话还没给过的全项目级坑，即使 AI 检索时关键词没对上，也能先看到这些坑和必须保持的行为。
  • “查过”的判定：MCP 的 search_memory，或终端里运行 pmem search --module <模块>。MCP 不可用时用终端也行，不会把 Agent 卡死。
  • 结束提醒：改了模块却没写记忆，提醒每个模块写一条功能记录，另有被排除的方向、根因或坑、约束、方案取舍时再写教训；回复结尾的“【pmem修改】”行里写了“模块 无需记录（原因）”的模块不提醒（按“；”分段，只认同一段里点名的模块；旧写法“【pmem】”也认）。只改了 gate.record_exempt 里的文件（默认是测试、生成代码、json/yaml/toml 等配置、Markdown 和 docs 目录）的模块不提醒。整个对话只查了记忆、没改也没写，也提醒一次，结尾写了“【pmem修改】本轮未改代码，无新结论”时不提醒（gate.analysis_reminder 可关）。中断结束的回合和说了“跳过记忆”的对话不提醒。提醒以“[pmem]”开头，用户不用处理；Claude Code、Codex 下以 Hook 反馈的形式出现（各版本都支持）。
  • 记忆审查（不改代码也生效，每个模块每个对话一次）：
    • 读代码时，附上该文件所属模块的现行教训摘要（每条只列一句话标题，排除项、风险优先，最多 6 条；关联代码之后改过的标“需核实”），另附至多 2 条关联代码就是这个文件的功能记录，再附上本对话还没给过的全项目级坑（至多 3 条，模块还没有记忆时也附），gate.read_digest 可关。
    • 在某个模块的文件或目录里 Grep、Glob、语义搜索时，同样附上摘要。
    • 回合结束时，本轮问题提到的、或本轮看过代码的模块有记忆、却既没查也没看过摘要，要求 AI 查过后核对回答，gate.question_review 可关。
    • Claude Code 在提问时就直接附上摘要；Cursor 不允许提问时注入内容，所以只能在结束时追问。
  • “跳过记忆”只在作为独立短语出现时生效；“如何避免跳过记忆”这类说法不算。生效后 AI 第一次读代码会收到说明（含触发它的原话），误触发时说“恢复记忆”即可。
  • 上下文压缩后状态清零；会话状态 7 天过期。
  • Hook 出任何异常都直接放行，错误写入用户缓存目录的 hook-errors.log；下一次工具调用或回合结束时，闸门会让 AI 在回复里提醒你“刚才闸门出错、那次没做记忆检查”，同一批错误只提醒一次。pmem doctor 显示近 24 小时的错误次数和最近一次内容。
  • 终端里的 pmem search --module 模块 要执行完、输出里看得到该模块才算查过；写在 || 之后或输出被丢弃都不算。
  • “需核实”的判定：关联代码写成 路径#函数名 时（Git 项目），只看这个函数在核对日期之后有没有改；只写了文件、SVN 项目或找不到函数时按整个文件判断。所以写记忆时 anchors 尽量写到函数。

Cursor 接入的 Hook 事件：sessionStart（经 .memory/bin/pmem-hook 调用，本机没装 pmem 时提示 AI 告诉用户安装）、beforeSubmitPrompt、preToolUse、afterMCPExecution、afterFileEdit、postToolUse（匹配 Read、Grep、Glob、语义搜索、Shell）、preCompact、stop。三个工具共用同一套闸门逻辑，统一调用 pmem hook <事件> --agent <工具>。

MCP 工具

MCP（Model Context Protocol，AI 调用外部工具的协议）服务由 pmem serve 提供，Agent 通过下面 5 个工具读写记忆。服务自带看门狗：崩溃、卡死（单次调用超过 server.request_timeout，默认 120 秒）或 pmem 升级后自动重启并重新握手，Cursor 不用手动重连；当时正在进行的调用会返回错误，重试即可。

工具用途主要参数
search_memory检索记忆。改代码前按文件或模块查一次path 或 module；可选 entity、query、limit（默认 5，上限 10）、as_of（按某天视角查）、full（本对话给过的也返回全文）、ids（按 id 取全文，给了就忽略其他条件）
record_memory写入一条记忆module、entity、kind、content；可选 summary、verify、applies、scope、supersedes、anchors、aliases、draft_id
confirm_memory核对后确认仍然成立，刷新核对日期ids
memory_graph模块全貌：每个议题的最新两条结论（过期的带 stale）和相关模块；带 entity 时看该议题的时间线（谁哪天替代了谁）module；可选 entity
list_modules列出模块、记忆数量和常用议题可选 category

检索结果里几个关键字段：items（教训，全文）、features（功能记录和规划，只有标题；改动会改变这些行为时先用 ids 取全文核对）、applies（适用条件）、stale（关联代码已变）、check（具体哪些文件变了）、fallback: module（议题内没命中，退回整个模块）、related（相关模块）、status（只在不是正式记忆时出现，如 seed）、seen（本对话已返回过全文，这次只给标题；上下文里找不到原文时带 full=true 重查）。同一对话的去重记录在上下文压缩后清空；终端里的 pmem search 由 Hook 在执行前交接对话 id，同样参与去重。MCP 不提供改状态的工具，转正、退回、归档只能由人在命令行操作。

配置

.memory/config.yaml 随仓库提交，团队共用。pmem init 生成的规则文件不要手改，重新 init 会覆盖；需要调整就改这里。

schema_version: 1
project:
  name: MyGame
  type: game
vcs: auto                   # auto / git / svn / none
svn_auto_add: true          # SVN 下新写的记忆文件自动 svn add
gate:
  mode: block               # block 检索成功返回才放行 / warn 只提醒一次 / off 只靠规则
  watch: []                 # 为空 = 所有已登记模块的路径都受守护
  ignore: ["**/*.md", "docs/**", ".memory/**", ".cursor/**", ".claude/**", ".codex/**", ".agents/**"]
  skip_markers: ["跳过记忆", "skip-memory"]       # 用户这样说时本对话不查也不写（须是独立短语）
  resume_markers: ["恢复记忆", "resume-memory"]   # 误判或改主意时，说这个重新打开
  stop_reminder: true       # 改了模块却没写记忆时，结束提醒一次

越用越收敛：项目越到后期维护，AI 越准、越快、越省 token。
  • 刚接入：记忆还少，大多查不到东西，准确性和耗时与没有记忆时差不多，每个对话小幅净增约 3000～5000 token。
  • 积累期：常改的模块有了根因、排除项和风险，同样的错开始不再犯，排查变短，少走的弯路开始抵消开销。
  • 维护期：老问题复发、改历史逻辑、换人接手时，直接拿到根因和结论；一条几百 token 的结论顶掉一次重新读代码、重新排查、重试已排除方向。
原因：单次开销不随记忆总数增长（见下）；踩过的坑、排除过的方向、更正都留了下来；零碎记忆还能合并（实测 13 条约 2500 字合并为 2 条约 1150 字）。
前提：记忆要准（pmem 自动标“需核实”并要求 AI 核对更正），不能太零碎（pmem doctor 提示时让 AI 按 pmem-compact 合并）。收敛有下限，最终趋向真正的新工作量；全新功能、还没有记忆的模块享受不到。
阶段趋势按机制推断，佐证是上一代系统的前后对比，pmem 自己的分阶段数据还没测；可定期用 pmem report 看本项目“用到记忆 / 未用到”两组对话的对比。
记忆变多不会让 token 线性增长。AI 不会直接读 .md 文件，只拿到检索返回的 Top-K：默认 5 条、上限 10 条，同一批次超过 2 条的往后排，被替代的不返回。单次调用的 token 只和返回条数有关，与库里总数无关。

检索与排序

  1. 按 modules.yaml 把文件路径或别名映射到模块，在模块内检索。
  2. 查询词按 synonyms 和记忆的 aliases 扩展，扩展词权重略低于原词。
  3. 相关度 = 0.6 × 向量相似度 + 0.4 × BM25（关键词匹配算法）。
  4. 议题匹配加 0.15；按文件检索时，关联代码（anchors）就是这个文件的加 0.3、同目录的加 0.1，模块里最近在改别的方面也不会把它挤掉；排除项、更正加 0.05；再乘时间系数 0.7 + 0.3 × 0.5天数/90：越新越靠前，最旧也保留七成（核对过的按核对日期算）。
  5. 同一批次（同一对话，或同一作者 90 分钟内）只有前 2 条按原位置排，超出的降到其他相关结果之后（仍在不相关的之前），避免碎片挤占名额，又不整条丢掉。
  6. 议题内没命中时退回整个模块，并标注 fallback: module。

分词：中文按二元组切分、英文按词，camelCase 拆开。默认语义模型 bge-small-zh-v1.5（ONNX 格式，约 90 MB），首次调用才加载。

实测：853 条真实记忆、13 个限定模块查询，前 3 条命中目标 pmem 9/13，原向量库服务 4/13；单次检索 1～14 毫秒。

整理与维护

合并零碎记忆（pmem-compact）

功能连续迭代几天常会写出十几条零碎记忆。对 Agent 说“按 pmem-compact 技能合并记忆”，它会读出议题全部正文，提炼成一两条现状并替代旧记忆。实测 13 条约 2500 字合并成 2 条约 1150 字。

整理同义词（pmem-normalize）

“闪退”搜不到只写了“崩溃”的记忆时使用。Agent 用 pmem terms 列高频词、起草词组，确认后写入 synonyms。

补关联代码

pmem anchors 从正文提到的文件名、类名.成员 自动补 anchors，补上后才能判断是否过期。

重建索引

换了嵌入模型或检索结果异常时运行 pmem reindex，同时会列出无法解析的记忆文件。

种子记忆（pmem-seed）

解决刚接入时记忆库为空的问题。Agent 读提交说明、文档和注释，用 pmem record --seed 写入；种子立即可检索并标“种子，待确认”。负责人用 pmem seed 过目后转正或退回。不做自动生成：哪些结论仍成立只有读懂才能判断。

归档

记忆已过时、又没有新结论可替代时用 pmem archive <id>。归档的记忆不再被检索到，它替代过的旧记忆也不会因此重新出现；文件保留在版本库可追溯。

模块改名与合并（pmem migrate）

rename A B：旧名登记为别名，读写自动转到新名。merge A B：A 的路径、别名、议题并入 B，A 标为 merged_into；A 是冷候选时登记为 B 的别名；A 是写入时自动新建的未登记模块（多半是笔误）时只搬记忆、不登记别名，确实是以后还会用的叫法才加 --alias。搬到一半失败时，按提示运行列出的 pmem migrate move / tidy 命令补完，不要重跑这次迁移。两者都会把记忆文件搬到新模块下（索引按文件里的模块名过滤，不搬就查不到）。队友迁移前写到旧名下的记忆，拉取后运行 pmem migrate tidy --apply。重写 modules.yaml 只保留文件开头的注释，预览时会提示丢失几行。deprecate A：业务下线时用，A 标为 status: deprecated，旧记忆照常可查，新写入被拒绝，改完 A 的代码也不再提醒写记忆；A 的路径仍归它，改代码前照样要先查。

split A --to B=路径：拆分。路径必须真的分走 A 的代码文件，不能抢别的模块的文件；A 里原样写着的路径直接移给 B。记忆按关联代码在新目录里的归属分配：都落在 B 就搬到 B，落在 A 或别的模块就留在 A；横跨 A 和 B 的、没写关联代码且同议题去向不一致的留在 A 并列出来，用 --assign 指定。--by entity 时把这些议题从 A 移到 B，对应记忆跟着走。

目录同步（pmem sync）

项目里新增了目录时运行。没被任何模块覆盖的代码按“第一个完全没有已覆盖文件的上级目录”分组：和已有模块同名、或是已有模块的又一个变体目录（同一父目录下它已有两个以上路径）的追加到那个模块；3 个文件以上且近 180 天有改动的成为新模块，否则成为冷候选；第三方目录追加到 third_party。冷候选有了记忆或改动 5 次以上时转正。近 90 天没改动也没记忆的模块只提示，不自动降级。

健康报告（pmem health）

给模块负责人定期收口用，只列有问题的段落并附处理办法；按 pmem-consolidate 技能可以让 Agent 逐节处理。检索、拒绝等数据只来自本机事件日志；“没人检索的模块”在本机检索少于 20 次时不统计。

“疑似互相矛盾的记忆”：同模块同议题、都还现行、一条是结论或决定而另一条是排除项或更正、正文用词高度相似（不比较风险类）。确实冲突就写更正替代过时的那条；两条都成立就 pmem confirm 较早那条，之后不再提示。

“未登记模块”：写入时用了 modules.yaml 里没有的模块名会自动新建。报告按这些记忆的关联代码给出建议登记的 paths（同一目录有 2 个以上文件的登记整个目录），并说明这些代码现在归哪个模块：都归同一个已登记模块的多半是写错了名字，用 pmem migrate merge 并过去；冷候选模块已有记忆的用 pmem sync --apply 转正。

“召回偏低”：现行教训 10 条以上、本机按模块检索 10 次以上，但被返回过的教训不到 30% 的模块（本机检索少于 20 次时不统计）。列出从没返回过的议题；常问却查不到的补 aliases 或登记同义词，议题太杂的用 pmem migrate split <模块> --by entity --to <新模块>=<议题> 拆开。功能记录在检索里只给标题，不参与这项统计。

“改了代码却没写功能记录”：按结束时需要记录的模块统计，回复“无需记录”的也列出，由负责人判断是否真的不用记。

清理候选只建议归档、从不删除，每条附判断依据（✓ 满足、✗ 不满足）。“建议归档”要同时满足：关联代码全部不存在（没写关联代码的看正文提到的文件和类，找到的不到 20%）、同议题没有其他现行记忆、没被其他记忆引用、统计期内本机没被用过（本机检索太少时不看这一条）。只满足一部分的列为“待核对”；排除项、风险、更正、全项目级和种子记忆最多到“待核对”。关联代码还有一处在的记忆不会成为候选。

记忆图（pmem map）

按模块分区、议题排时间线。红色是失败或纠错（排除项、更正），绿色是落地（结论、决定、功能），黄色是注意（风险），蓝色是未实现（规划），灰色虚框是已被替代或归档。实线是记忆里写明的替代，虚线是推断（同议题里排除项之后第一条落地的记忆，没写替代关系），“已撤销”是撤销过的合并。

顶部总评衡量存储结构是否完整：功能记录覆盖率、漏记（近期有提交、同期没有功能记录的模块）、断链（更正没写替代哪条，或同议题一正一反却没有替代关系）、悬而未决（只有排除项、后面没有落地）、过期。它不衡量记忆对 AI 有没有用，那要看 pmem report 和 pmem bench。Wiki 每个模块页也附一张 Mermaid 演化图（最多 40 个节点）。

迁移旧记忆

已有 LanceDB 版记忆库（如 tilematch-dev-memory）可以只读导入，源库不会被修改，重复执行会跳过已导入的条目：

常见问题

Windows 上 Hook 收到的中文是乱码？

这是 Cursor 在非 UTF-8 代码页下的转码问题，pmem 已自动兼容。开启 Windows 设置里的“使用 Unicode UTF-8 提供全球语言支持”可以从根本上避免。

终端里 pmem 的输出是乱码？

pmem 本身输出 UTF-8，直接看不会乱。Windows PowerShell 5 把输出再接给 Select-String、Select-Object 等命令时会按 GBK 解码，于是乱码。不要接管道，改用 --brief 看精简输出；确实要接时先运行 [Console]::OutputEncoding = [Text.Encoding]::UTF8。

第一次查询很慢？

首次使用会下载语义模型。提前运行一次 pmem doctor 即可预下载。

modules.yaml 写错了？

所有命令都会提示出错的行号；pmem doctor 还会检查覆盖率和路径重叠。

没有相关记忆，为什么还返回了几条？

检索总是返回得分最高的几条，由 Agent 读正文判断是否相关。真实数据上相关和不相关的得分区间重叠，设阈值会把真命中也挡掉，所以没加。把常用叫法写全比阈值更管用。

用 SVN 可以吗？

可以。作者和版本号取自 SVN，新记忆会自动 svn add，终端命令的事后比对也支持。按函数判断“需核实”目前只支持 Git。

对话里出现一条以“[pmem]”开头的消息，要我处理吗？

不用。这是回合结束时 pmem 自动发给 AI 的提醒（比如改了代码还没写记忆），Cursor 把它显示成一条用户消息。AI 会为改过的模块补写功能记录，再看本轮有没有被排除的方向、根因或坑、约束、方案取舍，有就补写教训；确实不用记时回复“无需记录：原因”，不需要你提供原因。

为什么做了功能也要记？不会变成变更日志吗？

功能记录写的是“谁要求的、哪些行为必须保持”，不是“改了哪个方法”。没有它，用户要求的行为看起来就像普通实现，后来的人（包括 AI）可能当成冗余改回去。功能记录在检索里只列标题、单独一组，教训照样优先、给全文，所以不会被挤掉；改某个文件时，关联到这个文件的功能记录会出现在读代码摘要和拦截提示里。

Hook 出错会卡住我吗？

不会。任何异常都直接放行，错误记在本机日志里；随后 AI 会在回复里提醒你一次“那次没做记忆检查”，用 pmem doctor 看原因。

队友没装 pmem 会怎样？

不会卡住，但闸门和审查都不生效。新对话开始时 AI 会收到提示，告诉他先安装；pmem doctor 也会检查。项目接入较早、没有 .memory/bin/pmem-hook 的，重新运行一次 pmem init。

多个项目会互相影响吗？

不会。每个项目的记忆在各自仓库的 .memory/，本机缓存按“项目名 + 路径哈希”分目录；只有语义模型是共享的。

已知限制

  • 收益报告只看本机数据，团队汇总尚未实现。
  • pmem bench 还没有用真实 API Key 跑过完整对照，示例用例只用 --dry-run 验证过。
  • 模块划分依赖 Agent 按 pmem-bootstrap 技能完成，还没有全自动扫描器。
  • Cursor 里 MCP 必须每人手动开启一次。
